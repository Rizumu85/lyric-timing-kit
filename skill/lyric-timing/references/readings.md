# 读音核对

词典只给每个词的默认读法，不看句子，也不知道作词人的特殊读法。读音核对的目的不是保证全对，而是把需要人听的范围缩小到少数几行。按下面的顺序做，前一层确认过的行不再进入后一层。

## 1. 找来源

来源指别人标注好的读音：带振假名的歌词页、歌词百科、卡拉 OK 视频、罗马音歌词页。

```text
node furigana_audit.mjs [key ...]        # 带振假名的歌词站
node moegirl_audit.mjs [key ...]         # 歌词百科里标出的特殊读法
node web_romaji.mjs [key ...]            # 通过用户浏览器搜索罗马音页
node search_karaoke.mjs                  # 找卡拉 OK 和彩色歌词视频
node video_sheets.mjs <key> <视频 id>    # 把视频抽帧拼成联系表，由 Agent 读出画面上的读音
python video_audit.py                    # 把读出的读音和现有读音比对
```

要点：

- **先验证是同一首歌**。脚本会比较页面歌词和手上歌词的重合度，重合不足的不采用。手动采用来源时也要做同样的确认。
- **固定站点找不到时，用搜索引擎再找一次**，不要直接下结论说没有来源。
- **来源只覆盖到的行才算核对过**。审计结果里的 `rows` 记录了实际比对的行，其余行仍然是词典读音。
- 比对出的差异逐条看过再应用（`node apply_furigana.mjs --write <审计文件>`）。自动匹配会产生错位的假差异，例如把相邻假名算进某个汉字的读音。
- 爱好者制作的罗马音偶有错字，只用来纠正明显的读音，不照抄。

## 2. 按上下文判断

```text
node unverified_lines.mjs > lines.txt
```

导出所有没有来源核对的行和现有标注，由 Agent 逐行阅读判断。这一步能纠正的典型问题：

- 常用词的默认读法不对：数词加“人”、量词的促音、叠词的连浊。
- 该训读的被读成音读，或反过来。
- 日语歌词里混入的简体字。
- 歌词表里混着的罗马音、译文，以及歌词表自带的错误注音。

只改确定的。作词人故意的特殊读法（例如把“命运”读成另一个词）上下文看不出来，留给下一层和人。

修改一律写成 `fix_lines.mjs` 的清单，不要整首重排。

## 3. 声学检查

```text
python reading_check.py --keys-file <file>      # 在词典给出的几种读法里，哪一种和录音更吻合
python reading_outliers.py --keys-file <file>   # 标注的读法在这一句的录音里听不听得到
```

两者互补：前者能给出建议读法，但只覆盖词典里有多种读法的词；后者不需要知道正确读法，能发现词典里没有的特殊读法，但只能说“不对劲”，且只对四个字母以上的读音可靠。

按实测，后者在现用阈值下大约抓到七成读错的词、误标约百分之五读对的词。所以它们的结果只用于在试听页上标记可疑行，**不自动应用**。

**听写结果也能判定特殊读法。** 版本核对留下的听写文本（`heard.json`）记的是模型实际听到的字。歌词表上的读音看着不对、又没有来源时，先看那一句听写成了什么，再看译文里有没有括注。例：歌词表把四个不同的名词都标成同一个读不通的读音，而听写在这四句听到的是同一个常用的代词，译文里对应的位置也写着“（你）”，就可以确定这四处都唱那个代词，不必让用户去听。

## 4. 交给人

试听页只在“没有来源核对、并且声学检查认为可疑”的行上显示标记。用户听过后用备注写出实际读法，再按 [试听与反馈](review.md) 处理。

## 其他语言

- 韩语：写入和试听时自动在每个韩文字上标罗马音，并处理连音。不需要额外步骤。
- 中文歌夹杂外语片段时不加译文。
