# 流程与命令

命令都在 `tools/` 目录下运行。`<key>` 是一首歌的标识（音乐文件路径的哈希前 12 位），也是它数据文件夹的名字。带 `--keys-file` 的脚本接受一个每行一个 key 的文件。

## 每首歌的文件

| 文件 | 内容 | 谁写 |
| --- | --- | --- |
| `source.json` | 歌词表：每行原文、译文、原始时间。读音写在汉字后面的括号里 | 导入；之后只由人或 Agent 明确修改 |
| `prepared.json` | 上一次打轴时每行实际使用的读音 | 打轴 |
| `aligned.fia` | 草稿：逐字时间和注音 | 打轴、单行修改 |
| `aligned.in-file.fia` | 已写入的歌被重新打轴时，音乐文件里那一版的副本 | `onepass.py` |
| `ja-emission.pt` | 对齐模型对分离人声的逐帧输出（20 毫秒一帧），重排时直接复用 | 打轴 |
| `mix-reading.json`、`second-reading.json`、`vocals-readings.json` | 不看歌词的几路读法：对齐模型听原曲、第二个模型听原曲、两个模型听 BS-RoFormer 人声 | `onepass.py` |
| `result.json` | 状态。`complete` 表示已写入，`confirmed` 表示人确认过 | 各阶段 |
| `timing-edits.json` | 用户在试听页上的手动调整，写入时合并进草稿 | 试听页 |
| `timing-edits.applied.json` | 已经并进草稿的手动调整的累计记录；记录里的行就是“人放过的行”，重排时原样保留 | 写入、`onepass.py` |
| `line-notes.json` | 用户写给 Agent 的逐行备注 | 试听页 |
| `heard.json`、`lyric-check.json` | 听写结果，以及它和歌词的差异 | 版本核对 |
| `reading-check.json`、`reading-outliers.json` | 两种声学读音检查的结果 | 读音核对 |

`source.json` 是唯一的事实来源。要改歌词或读音就改它，再让对应的行重新对齐；不要直接改草稿里的文字。

### 读音的写法

- 汉字后面加括号：`運命(さだめ)`。括号里可以是平假名、片假名或罗马音；片假名会原样显示。
- 被注音的部分不全是汉字时，用 `｜` 标出起点：`｜夜の手(ナイトハンド)`。

## 阶段命令

### 1. 清点与导入

```text
python batch_inventory.py                # 首次：清点音乐目录里的 MP3，取出内嵌歌词
python add_songs.py                      # 登记还没登记的文件（各种格式；首次清点后也跑一遍，把非 MP3 的补上）
python set_lyrics.py <key> <歌词文件> [--write]   # 文件没有内嵌歌词、或内嵌的是错的时，换上一份歌词表
node dropped_text_scan.mjs               # 导入检查：被误删的行、掉落的词
node mixed_translation_scan.mjs          # 导入检查：粘在原文后面的译文
node clean_credits.mjs [--write]         # 制作信息、歌手名单
python fix_simplified_kanji.py [--write] # 日语歌词里混入的简体字
node find_translation.mjs <key> && node apply_translation.mjs <key>   # 缺译文时从音乐平台补
```

#### 译文缺行时去哪找

平台上的译文经常只缺几行：一行歌词被拆成两半时后半句没有译文，英文句和数拍子的句子没有译文。`find_translation.mjs` 只查音乐平台，查不到时按这个顺序找，不要直接自己翻：

1. **音乐平台上同一首歌的其他版本**：原唱、翻唱、现场版的译文往往出自同一份。
2. **视频站上带中文字幕的上传**：搜“歌名 + 中文字幕”或“歌名 + CC字幕”，优先选标题写明 CC 字幕的。CC 字幕是文本，只取字幕、不必下载视频（例如 `yutto --subtitle-only <视频地址>`，得到带时间的 `.srt`），几秒钟就能拿到整首的原文和译文对照。字幕烧在画面里的视频要抽帧再读，成本高得多，排在后面。
3. **都没有才自己翻译**，并告诉用户哪些行是自己补的。

采用前先拿已有的几行对比措辞：一致说明是同一位译者，直接补缺行；不一致就不要把两种译文混在一首歌里。字幕里原样保留的外语句（如 `Sit down`）保持不译。字幕按整句写、歌词表按半句拆时，把译文拆到对应的半句上。

### 2. 打轴

```text
python batch_align.py                    # 全部未打轴的歌；打完自动接着跑 onepass（日语歌，以及歌词表带时间的其他语言；--no-refine 关掉）
python onepass.py <key> ...              # 预览：给以前打过轴的歌按新办法重定时间
python onepass.py <key> ... --separate --write   # 写草稿并送上试听页；--separate 多做一次 BS-RoFormer 人声分离
python onepass.py --eval-hand [<key> ...]        # 只读：人手动放过的行，工具现在自己会放在哪
python realign_song.py <key>             # 按 source.json 重新打一首
python realign_song.py --anchor-embedded <key>   # 文件里已有歌词时，以其中的句首时间为锚
node realign_keys.mjs <keys file>        # 批量重排，自动为每首选择上面两种方式
node pin_to_source.mjs <key> <行号> ...  # 对不出来的行（拖长的哼唱、打码的词）放回歌词表的时间
```

#### onepass 做了什么

下面说的是日语歌。其他语言见这一节末尾的“日语以外的歌”。

第一次强制对齐只负责定结构，时间由 `onepass.py` 重定。它把三种信息各用在擅长的地方：

1. **不看歌词的读法**定“每个音在哪”。对齐模型逐帧读出它听到的音，第二个模型（RomajiASR）逐个报出它听到的拍；各读原曲和分离后的人声，一首歌最多五路。歌词里连着对上三个音以上的，钉在听到的时刻。对齐模型按字母比，第二个模型按“音”比：辅音同族或元音相同就算相近（它常把 zu 听成 tsu、把英语按片假名读，但个数和节拍是对的）。
2. **投票**。同一个模型读不同版本的录音容易一起错（重复的词都对到同一处错的地方），所以第二个模型的两路读法一致时直接采用，不被对齐模型的几路否决；只有一路有异议时，这个音谁都不信，留给第 4 步。
3. **歌词表的时间**只划范围：每句在“自己的时间前 2 秒到下一句时间后 2 秒”里找（一句最多延到 6 秒后，逐拍比对时 12 秒），并算出整首相对歌词表的偏移。有重复时取离歌词表时间最近的那次。
4. **按歌词整首对齐一遍**，只填没钉住的音，夹在钉住的音之间。一段声音只归一个字，所以下一句不会抢上一句的句尾。

之后的收尾规则：每句最后一个字至少留 0.2 秒、不拖进后面歌词里没有的念白；人放过的行原样保留，并且就在人放的位置附近比对；整句是拉丁字母、两个模型又听出不到一半的英语句，交给多语对齐模型按英文单词重排。

它会给这些行加标记，标记会出现在试听页上，也会让这首歌不能自动写入：

| 标记 | 含义 |
| --- | --- |
| 这句的音模型大多没听出来 | 位置是按歌词表时间推的 |
| 平台歌词时间那里没听到这句，在某处听到了 | 两路读法在同一处找到，已搬过去 |
| 这句比平台歌词的时间早/晚若干秒 | 和整首的偏移差 1 秒以上 |
| 英语句……用英语对齐模型排的 | 句内时间来自另一个模型 |

重新对齐已经写入过的歌时用锚定方式。按歌词表原始时间开窗的方式会让整句提前约一秒，只在歌词表时间可信而整曲对齐明显失败时使用（`--windowed`）。

### 3. 歌词版本核对

```text
python transcribe_song.py <key>          # ASR 环境；中文歌用 transcribe_zh.py
python lyric_check.py <key>
```

`unheard` 是歌词里有但没听到的行，`extra` 是听到但歌词里没有的内容。英语和快节奏段落的误报多，判断前看具体内容。

### 4. 读音核对

见 [读音核对](readings.md)。

### 5–6. 试听与反馈

```text
node review_server.mjs                   # 试听页，默认 http://127.0.0.1:3417
node fix_lines.mjs <edits.json>          # 单行修改：改词、改读音、删行
```

`fix_lines.mjs` 的输入：

```json
{ "<key>": { "replace": [[行号, "原文片段", "新片段"]], "remove": [行号], "removeFrom": 行号 } }
```

它只重新对齐被改的行，并保持该行原来的句首时间；用户的手动调整留在各自的行上。删行之后 `prepared.json` 不会跟着变，下次要用 `onepass.py` 重排这首歌之前，先把里面对应的行删掉或重新打轴一遍，否则会报“draft, pronunciations and lyric sheet are out of step”。

### 7. 写入

```text
node embed_confirmed.mjs <key> ...           # 人确认过的歌
node rerun_gate.mjs                          # 自动重排后，判断哪些歌可以不经试听写回
node embed_confirmed.mjs --rerun <key> ...   # 写回通过上一步的歌；不会碰人确认过的歌
```

各种格式的写法见 [环境与模型](setup.md) 的“音频格式”。第一次写某种格式时，先写一首并回读确认，再写其余的。写完告诉用户：播放器里要重新扫描或重新导入这些文件，否则显示的还是它缓存的旧歌词。

自动写回的条件由 `rerun_gate.mjs` 判定：行能一一对应、没有任何一行比文件里现有的时间移动超过 3 秒、移动超过 1 秒的行不超过一成。不满足的留给人听。

## 歌名

```text
node title_translations.mjs              # 查音乐平台上的通用译名
node review_server.mjs  → /titles        # 用户逐首选择是否加译名
python apply_title_choices.py [--write]  # 改文件名和标题标签，并迁移数据文件夹
python retitle.py "<文件名片段>" "<新译名>"
```

改文件名会改变 key，所以必须用这两个脚本，不要手动重命名。

#### 日语以外的歌

英语、中文和混合语言的歌用同一个 `onepass.py`，区别只有三处：

- **读法都来自同一个模型**：多语言对齐模型不看歌词直接读，读三份声音：流程自己分离的人声（存下来的 `mms-emission.pt`）、原曲、BS-RoFormer 分离的人声，三路照日语歌的规则投票。日语的第二个模型（RomajiASR）和英语句补对齐是日语专用的，这里不用，所以没有“训练数据不同的第二个模型”来纠正它们一起听错的地方。
- **按音近比对，不按拼写**：这个模型写的是它听到的音，不是这门语言的拼写（credit 读出来是 krede，青 qing 读出来是 jing）。所以歌词和读法按音的类别比：元音算一类，b p f v 一类，d t 一类，l r 一类，咝音一类；y、w 和 sh zh ch ng 的第二个字母不单独算音。英语单词先按发音词典改写成读音再比。改成这样之后，中文歌能认出一半左右的字，英语歌三分之一左右（按字母比只有三成和两成）。
- **更保守**：几路读法出自同一个模型，会在同样的地方一起听错，两路一致不能当证据。所以这里不做“在别处听到就把整句搬过去”；听到的位置如果让这一句离预期超过 1.5 秒，也不采信，这一句按歌词表的时间放。试过不加这两条：多读两份声音后有的行被对到几秒外的重复句上。加上之后，三路比一路多认出约一成的字，句首的准确率持平。
- **门槛不同**：这个模型听唱歌本来就听得少，整首认出的比例低于 10% 才不采用（日语是 50%）；“这句模型没听出来”的提示只在它跟得上的歌里（整首认出一半以上）才给。

为什么非日语歌也要走它：以前这些歌只做整首强制对齐，重复的句子、吟唱、间奏后的句子经常整句对到几秒外。在一个有 94 首非日语歌的库里，人手动改过的 318 行，改之前中位数偏 3.4 秒，只有 8% 在 1 秒以内；`onepass.py` 不看这些人工结果从头跑，97% 落在人放的位置 1 秒以内。句尾压到下一句的行从 126 行变成 0。代价是歌词表时间本身就错的行会跟着错（约 2% 到 3% 的行），这些要靠试听。

歌词表不带时间的歌没有“每句大概在哪”可用，仍然只做第一次强制对齐。
