# lyric-timing

## 目标

把“歌词文本 + 音频”变成写进音乐文件的逐字歌词，并且让人只看必须由人判断的地方。自动打轴本身不难，难的是不知道哪里错了：读音标错、歌词版本和录音不一致、时间整句偏移。这个 Skill 的流程围绕一件事设计：机器能确认的由机器确认，确认不了的缩小成几行交给人。

三条贯穿全程的约束：

- **没有被人确认的内容不写进音乐文件**，除非它通过了本流程明确规定的自动条件；写之前一律先备份原文件。
- **人确认过的歌只做单行修改**，不整首重新打轴，否则会推翻人已经听过的时间。
- **会改写数据的脚本只在明确要求时运行**。检查脚本能否加载只做语法检查，不要通过导入或空参数运行来试，它们会直接在真实数据上执行。

## 首次使用

1. 读 [环境与模型](references/setup.md)，确认仓库、配置文件、两个 Python 环境和模型是否就绪。缺什么补什么，已有的不要重装。
2. 下载模型、安装依赖、登录网站、读取用户浏览器都要先说明用途并取得同意。
3. 配置里的音乐目录是用户的原始文件，除了“写入”阶段，任何步骤都不修改它。

## 工作流

每个阶段的命令和产物见 [流程与命令](references/pipeline.md)。按阶段推进，不跳过自检。

1. **清点与导入**：登记音乐文件，取出已有歌词（文件内嵌的或用户提供的）。导入后立刻跑导入检查，原因见 [常见陷阱](references/pitfalls.md)。
2. **打轴**：人声分离后做强制对齐，得到每首歌的草稿。
3. **歌词版本核对**：用听写结果和歌词逐句比对，找出多唱、少唱和不属于这个录音的行。
4. **读音核对**：按 [读音核对](references/readings.md) 的顺序做，目的是把“可能读错”的范围缩小到少数几行。
5. **交给人**：启动试听页，告诉用户入口和每首歌要听什么。用法和反馈的处理方式见 [试听与反馈](references/review.md)。
6. **处理反馈**：用户标了“通过”且没有未处理备注的歌直接写入；有备注的先按备注改，再决定写入还是退回。
7. **写入**：写入前自动备份，写入后回读校验，音频数据或其他标签有任何变化就中止并保持原文件不变。写完提醒用户让播放器重新读取这些文件，否则播放器里还是它缓存的旧歌词。

## 关键判断

- **整首重排还是单行修改**：歌词行数变了、或整首偏移时才整首重排，并且重排后要退回给人重听；其余一律单行修改。
- **来源能不能信**：任何外部来源（歌词页、卡拉 OK 视频、罗马音页）先确认它的歌词和手上这首对得上，再采用其中的读音或时间。同名不同曲很常见。
- **用户的备注怎么读**：备注里写的读音如果和现有的一样，是在确认，不要改；带问号的是用户不确定，先找来源或按上下文判断，采用后在汇报里说明是推断。
- **拿不准就不改**：读音、歌词拿不准时保留原样并明确告诉用户，不要为了显得完整而猜。
- **适配按类别做全**：遇到一种没处理过的情况（新的音频格式、新的歌词写法）时，先弄清同类还有哪些，一次处理完并逐类验证，不要只修眼前这一个。

## 输出

- 音乐文件里的两份内嵌歌词：普通双语 LRC 和带逐字时间与注音的 Ruby LRC。
- 每首歌一个数据文件夹（歌词表、草稿、检查结果、备份记录），位置由配置决定。
- 每轮结束时向用户汇报：写入了哪些歌、按备注改了什么、哪些是推断、哪些退回重听以及要听哪里。
